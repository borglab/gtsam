BatchFactor Performance Notes

How the BatchFactor path was reshaped in this workspace to avoid dense materialization and become competitive with the existing Jacobian/QR fast path.
Status: documentation-only request Scope: BatchJacobianFactor, MultifrontalClique No code execution performed

1) What BatchFactor is in this codebase

In this branch, BatchJacobianFactor is a compact row-sparse representation for many small Jacobian blocks (typical of factor batching). It stores only the nonzero variable blocks per row group plus RHS blocks, not a dense Jacobian over every key in the factor.

  • Core type: BatchJacobianFactor<ErrorDim, BlockDims...> in gtsam/linear/BatchJacobianFactor.h.
  • Base interface: BatchJacobianFactorBase exposes a fast path through scatterInto() and two direct Hessian routines.
  • Compatibility still exists: toJacobianFactor() creates a dense-block factor when needed.

Fast path contract

Direct paths write only needed blocks, accept precomputed clique-local block indices, and can update SymmetricBlockMatrix directly.

Why this matters

Many batching workloads had huge overhead from zero-padding and repeated key lookup in hot loops.

2) Why the original generic path was slow

Legacy processing tends to do this: factor is converted or expanded into a dense-block Jacobian, then written into the clique matrix and multiplied through BLAS/RankUpdate. That path is correct but expensive when factors are sparse in key coverage.

Cost center Impact
Dense block materialization Alloc/fill overhead plus mostly zero entries for absent keys.
Repeated key->slot lookup in elimination assembly Linear-time overhead per row group per pass and branchy lookups.
Extra passes between factor load and Hessian assembly More memory traffic than necessary for already-whitened batch structure.
Constraint/fixed key edge cases handled late Branches in hot loops and fallback conversion paths.

For dense and moderately sparse graphs this is acceptable; for batch-heavy structures it becomes a major fraction of total solve time.

3) Optimizations introduced

3.1 Row-sparse storage + explicit slot mapping

The batch factor keeps per-row-group slot indices into its local key list and fixed-size Jacobian blocks. That avoids storing structural zeros and keeps Hessian updates tied to only active variables. 

// public API in BatchJacobianFactorBase
virtual void scatterInto(VerticalBlockMatrix& target,
                        size_t rowOffset,
                        const std::vector<DenseIndex>& targetBlockIndices) const = 0;
virtual void updateHessian(const std::vector<DenseIndex>& slotIndices,
                          SymmetricBlockMatrix* info) const = 0;
virtual void updateHessian(const std::vector<DenseIndex>& slotIndices,
                          SymmetricBlockMatrix* info,
                          DenseIndex beginCol, DenseIndex endCol) const = 0;
virtual void buildMappedSlots(const std::vector<DenseIndex>& slotIndices,
                             std::vector<DenseIndex>& mappedSlots) const = 0;
virtual void updateHessianWithMappedSlots(
    const std::vector<DenseIndex>& mappedSlots,
    SymmetricBlockMatrix* info) const = 0;

This API change makes downstream code choose either QR-style scatter or direct Hessian updates without conversion.

3.2 Cached load plans in MultifrontalClique

Clique loading now builds per-factor metadata once in FactorLoadPlan:

Field Purpose
blockIndiceskey slot map for each factor key (or -1 if fixed)
blockIndicesWithRhssame as above + RHS block index
mappedSlotsflattened row-group-local mapping reused by direct hessian update
canDirectUpdateruntime predicate for the fast path (no fixed-key + unconstrained model + supported type)
flags allBatchFactors_, hasDirectBatchFactors_choose whether to skip Ab fill and call batch-only direct assembly

The load plan is built once per clique and reused across solve iterations, removing repeated factor-type checks and key mapping in hot paths.

3.3 Direct Hessian updates when allowed

In elimination, when non-QR and direct batching is enabled, the clique can skip regular Ab assembly for eligible factors and update information blocks directly. 

if (allBatchFactors_ && !useQR() && kUseDirectBatchHessianUpdate) {
  fillRows_ = 0;
  RSdReady_ = false;
  return;
}

During preparation: 

if (canUseDirectBatchHessianUpdate &&
    (allBatchFactors_ || hasDirectBatchFactors_)) {
  for each plan where plan.canDirectUpdate && kind==Batch:
    if (plan.mappedSlots.empty())
      batchFactor->updateHessian(plan.blockIndicesWithRhs, &info_);
    else
      batchFactor->updateHessianWithMappedSlots(plan.mappedSlots, &info_);
  if (fillRows_ > 0 && !allBatchFactors_)
    info_.selfadjointView().rankUpdate(Ab_.matrix().topRows(fillRows_).transpose());
}

For mixed graphs, the matrix first receives direct batch updates for direct-compatible factors and then rank-updates the remaining rows from Ab_.

3.4 Mapped-slot buffer and branch elimination

For direct Hessian paths, each row-group slot mapping is pre-expanded to a flat array where every row contributes NumSlots+1 entries (all key slots + RHS slot): 

mappedSlots.resize(rowSlots_.size() * (NumSlots + 1));
// contiguous: [row0_slot0,row0_slot1,...,row0_rhs,row1_slot0,...]

During updates, kernels iterate with compile-time unrolled loops over active variables in a row-group, and work from pre-resolved indices. This reduces per-factor branch checks and random indirections.

3.5 Safety & compatibility guardrails

Fast path is selective, not universal.

  • Constrained noise models are rejected in direct hessian update, matching existing Jacobian behavior.
  • Fixed keys are mapped to -1; if present in a batch factor, canDirectUpdate becomes false and fallback paths are used.
  • Non-batch factors still follow existing JacobianFactor loading and are unchanged.
  • QR mode currently continues through existing QR code path; direct batch hessian update is disabled there.

compile-time switch in MultifrontalClique.cpp controlling availability of the batch direct path.

4) Why this should move the needle by ~10%+

4.1 Reduced memory traffic

Avoiding full dense conversion removes both writes and cache churn for zero blocks in batch factor rows.

4.2 Less control-flow in hot loops

Slot mapping done once, reused over iterations. Hot loops consume mapped indices directly and run the same unrolled templates repeatedly.

4.3 Better elimination locality

With all batch-compatible factors in a clique, elimination can avoid populating Ab_ rows at all, and update info_ directly.

4.4 Lower allocation pressure

No temporary dense JacobianFactor for the direct path, especially relevant in repeated linearized solves.

5) Current caveats

5.1 Path coverage

Only the Cholesky-style pipeline gets the full direct-Batch benefit; QR path still uses the existing fast path behavior.

5.2 Model constraints

Constrained models are intentionally excluded from direct hessian updates to remain behavior-compatible.

5.3 Mixed cliques

Mixed factor sets still pay a partial fallback cost, though reduced vs legacy baseline.

6) Biggest next improvements (targeting the next 10%+ gains)

Near-term work with the highest leverage:

  1. Switch kUseDirectBatchHessianUpdate from a compile-time constant to a runtime auto-tuned flag. It is safer to disable direct updates for tiny cliques where setup overhead dominates.
  2. Cache contiguous per-row pointer tables for block payloads and per-factor RHS/model weights so the direct update loop is strictly pointer arithmetic (very low-level kernel style).
  3. Specialize/update kernels for the most common (ErrorDim, BlockDims...) signatures (e.g., camera/landmark patterns) to remove template-index overhead from indirect accesses.
  4. Parallelize direct batch hessian updates at clique level where cliques have enough independent rows and few children, instead of serial in all direct cases.
  5. Store plan metadata as POD-friendly fixed-size structures for better locality (avoid scattered vectors inside many plans).
  6. Precompute and cache branch masks for fixed/constrained/fallback eligibility in solver warmup to reduce dynamic checks in each iterate.
  7. Collect microbenchmarks by factor sparsity and row-group size and split heuristics into three bins: direct all, mixed-direct, and fallback-all.

7) End-to-end view

For each clique:
1) Build factor load plans once (kind, slot maps, direct flag, mapped slots)
2) fillAb():
   - if all factors direct-compatible and non-QR, skip writing Ab rows
   - else emit Jacobian rows and/or scatter batch rows as needed
3) prepareForElimination():
   - if direct batch mode enabled and applicable:
       for each direct batch plan -> updateHessian() or updateHessianWithMappedSlots()
   - then fallback rankUpdate of any remaining non-direct rows (if mixed)
4) factorize() unchanged (Cholesky or QR)
5) updateSolution() unchanged, children gather unchanged

8) Quick take

The practical improvement comes from matching representation to algorithm: BatchFactor already has compressed structure, so we now exploit that structure through cached slot mappings and direct information-matrix updates. This is the dominant optimization path for batch-heavy graphs and is the right structural direction for a >10% uplift.
