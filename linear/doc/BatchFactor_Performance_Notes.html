BatchFactor Infrastructure and Performance Notes

A practical map of how batch factors are represented, assembled, and solved in GTSAM linear, plus the optimizations that keep them competitive against dense Jacobian paths.

1) Big-picture view of the batch infrastructure

In this stack, batch support is not a single class; it is a small cross-cutting path that runs through factor interfaces, factor-graph conversion, precompute/elimination planning, and clique-level assembly. 

          graph TD
            A[GaussianFactorGraph] --> B[Graph contains JacobianFactor or BatchJacobianFactor]
            B --> C[MultifrontalSolver::Precompute]
            C --> D[buildIndexedJunctionTree + fixedKey handling]
            C --> E[Leaf merge heuristics + ordering reductions]
            D --> F[MultifrontalClique buildLoadPlans]
            F --> G[FactorLoadPlan: kind + slots + direct eligibility]
            F --> H[fillAb()]
            F --> I[prepareForElimination()]
            H --> J[Ab_ accumulation]
            I --> K[SymmetricBlockMatrix info_ updates]
            J --> L[rankUpdate + elimination]
            K --> L
            L --> M[Multifrontal solve/updateSolution]

So the infrastructure spans:

Factor representation layer

BatchJacobianFactorBase and concrete BatchJacobianFactor<...> hold the compact row-group structure.

Graph interoperability layer

GaussianFactorGraph consumes both dense Jacobian factors and batch factors, converting batch factors to dense only when required by APIs.

Solver planning layer

MultifrontalSolver::precomputeFromGraph validates supported factor types and builds the symbolic graph + fixed-key bookkeeping.

Clique execution layer

MultifrontalClique::buildLoadPlans and execution paths decide whether direct batch updates are legal per factor.

2) How to use BatchFactor in the nonlinear API

BatchFactor is the public nonlinear API for grouped factors. It wraps many homogeneous factor instances into one NonlinearFactor, then linearizes all rows together into a compact BatchJacobianFactor when constraints and dimensional assumptions permit.

Why it exists

Avoid per-factor overhead in large repeated structures (e.g., many feature-track observations) while preserving exactly the same nonlinear objective.

What it changes in user code

You still build a NonlinearFactorGraph; only factor construction style changes from many individual factors to one batched wrapper.

What it does not change

Solver selection and objective semantics stay identical; only linearized representation and assembly internals are altered.

2.1 Construction patterns

Choose the constructor based on your data layout:

  • Build from a vector of pre-created factors (copies or moves).
  • Build from map constructors where one key is fixed and the other varies.
  • Let the helper detect factor constructor signatures (measurement-first vs key-first forms).
using ProjectionFactor = GenericProjectionFactor<Pose3, Point3, Cal3_S2>;

// Vector constructor
std::vector<ProjectionFactor> factors;
factors.emplace_back(meas_i, model, x_i, l_i, K); // repeated
auto batch = std::make_shared<BatchFactor<ProjectionFactor, 2>>(factors);

// Map constructor
std::map<Key, Point2> z_by_landmark;
auto batch2 = std::make_shared<BatchFactor<ProjectionFactor, 2>>(
    poseKey, z_by_landmark, model, K);

2.2 Standard solve flow

NonlinearFactorGraph graph;
graph.add(batch);

Values initial;
initial.insert(...); // same keys as factor constructor keys

LevenbergMarquardtOptimizer optimizer(graph, initial);
Values result = optimizer.optimize();

When batching many factors, the objective remains the same; only the Jacobian assembly path is more compact and more cache-friendly for repeated rows. 

// Optional: keep behavior as a HessianFactor output path
batch->setUseHessianFactor(true);

2.3 Mapping from user API to linear internals

  • BatchFactor::linearize is called by nonlinear optimizers during each iteration.
  • If all key dimensions are fixed and noise models are unconstrained, linearization builds BatchJacobianFactor<ErrorDim, BlockDims...>.
  • If dimensions are dynamic or constrained noise appears, it falls back to a dense JacobianFactor path.
  • That dense factor still has identical algebraic meaning; it only changes storage/assembly cost.
// Conceptual branch inside linearize()
if (hasFixedDimensions && !hasConstrainedNoiseModel)
  return linearizeToBatchJacobian(values, fixedDimensionsIndexPack);
else
  return linearizeToJacobianFactor(values);

2.4 timeSfMBAL-style example from this repo

The test suite contains a direct analog to timeSFMBAL-style batching in testBatchFactor.cpp: multi-camera observations of the same point (batched by landmark). 

using Factor = GeneralSFMFactor<PinholeCamera<Cal3_S2>, Point3>;

std::vector<Factor> factors;
Key camera1 = Symbol('c', 1), camera2 = Symbol('c', 2), point = Symbol('p', 1);
Point2 z(0, 0);
auto noise = noiseModel::Unit::Create(2);

factors.emplace_back(z, noise, camera1, point);
factors.emplace_back(z, noise, camera2, point);

BatchFactor<Factor, 2> batch(std::move(factors));
auto gaussian = batch.linearize(values); // yields compact batch Jacobian when fixed-dim assumptions hold

This is exactly the pattern where structure-aware batching helps most: repeated factor type, small residual dimension, and highly structured key reuse.

3) Full batch infrastructure, component-by-component

3.1 BatchJacobianFactorBase and BatchJacobianFactor

This is the API boundary for batch-specific execution in linear space. The base class exposes both:

  • standard Gaussian-factor compatibility methods inherited from the solver contract, and
  • batch-specialized routes used by the direct fast path.
// Base batch interface used by solver/clique fast paths.
template<...> class BatchJacobianFactorBase : public GaussianFactor {
  virtual size_t scatterInto(VerticalBlockMatrix& target,
                             size_t rowOffset,
                             const std::vector<DenseIndex>& targetBlockIndices) const = 0;
  virtual void buildMappedSlots(const std::vector<DenseIndex>& slotIndices,
                               std::vector<DenseIndex>& mappedSlots) const = 0;
  virtual void updateHessianWithMappedSlots(const std::vector<DenseIndex>& mappedSlots,
                                           SymmetricBlockMatrix* info) const = 0;
};

Concrete class BatchJacobianFactor<ErrorDim, BlockDims...> stores compact row groups and compact RHS/blocks instead of fully dense row blocks for all keys.

3.2 Conversion and compatibility in GaussianFactorGraph / JacobianFactor

Where an API expects a true JacobianFactor, batch factors can be converted via toJacobianFactor(). This keeps compatibility for older paths but is intentionally avoided on hot direct paths.

The compatibility path is necessary for:

  • error reporting utilities and generic factor operators expecting standard augmented Jacobians,
  • fallback solver paths that are not batch-aware, and
  • mixed-factor debugging and generic math tools that are factor-type-agnostic.

3.3 Solver front-end and planning in MultifrontalSolver

The solver front-end explicitly accepts only Jacobian-like inputs:

  • JacobianFactor
  • BatchJacobianFactor (through BatchJacobianFactorBase)

During precompute, fixed keys and row counts are collected, and factor metadata is prepared once for repeated optimization passes where available.

3.4 Clique assembly in MultifrontalClique

The crucial structural decision is made per factor in a reusable FactorLoadPlan:

Plan fieldMeaning
kindJacobian vs Batch factor path in that clique
blockIndicesslot index per key (or -1 for fixed keys)
blockIndicesWithRhssame vector plus RHS slot index
mappedSlotspre-expanded dense-index mapping for direct hessian kernels
canDirectUpdatedirect batch eligibility (model/constraint/fixed-key conditions)
modelcached noise model pointer for fast checks

This is built once, then reused for each solve iteration in a given graph structure.

3.5 Stable infrastructure around the batch fast path

The batch machinery sits inside the standard multifrontal stack rather than replacing it:

  • symbolic analysis and elimination ordering already come from existing sparse elimination settings and frontal tree construction,
  • GaussianFactorGraph still drives error models, linearization bookkeeping, and factor ownership,
  • numeric elimination, QR fallback, and linearization residual handling stay in their established components, and
  • factor-tree merging/leaf controls still determine the clique decomposition before batch-aware plan execution starts.

This separation is why the batch updates can be measured independently: only specific clique-level kernels were touched for performance, while the broader solve contract remains intact.

4) Execution path: from factor graph to update

4.1 Fallback path (safe baseline)

For unsupported combinations, batch factors are materialized into Jacobian form and processed through the established Jacobian/Ab accumulation path. 

fillAb() : for each plan
  if Jacobian factor -> addJacobianFactor()
  if Batch factor but not direct -> addBatchJacobianFactor()
prepareForElimination() : rankUpdate(Ab_)
factorize()

4.2 Direct batch path (fast path)

For direct-eligible batch factors, the clique updates info_ directly using mapped slots and prewhitened rows. This avoids materializing rows into Ab_ in full.

The mapped-slot kernel now intentionally uses the checked update path for all inputs: negative slots are treated as fixed/skip markers, while slots above the RHS block still trigger the same validation error as before. The previous unchecked “all slots non-negative” branch was removed to simplify control flow; numerical behavior and API contracts were kept unchanged. 

if (canUseDirectBatchHessianUpdate && (allBatchFactors_ || hasDirectBatchFactors_)) {
  for each direct Batch plan:
    batchFactor->updateHessianWithMappedSlots(plan.mappedSlots, &info_)
  if (fillRows_ > 0 && !allBatchFactors_)
    info_.selfadjointView().rankUpdate(Ab_.topRows(fillRows_).transpose())
}

4.3 Constraint and mode guardrails

  • Constrained BatchJacobianFactor is rejected for direct batch updates in current implementation.
  • If a batch factor has fixed keys, direct update is disabled for that factor and fallback path is used.
  • QR mode keeps the existing QR flow; direct batch Hessian is a non-QR path optimization.
This split is intentional: the goal is performance without changing solver semantics.

4.4 Symbolic and merge-stage interactions

Before numeric elimination, MultifrontalSolver may merge leaf batches and child clusters using configurable thresholds. This affects the number and composition of cliques reached by each elimination pass, which in turn changes direct-vs-mixed behavior inside each clique.

5) Why this changed the performance profile

The speedup is from reducing repeated structural work that grows with batch size and factor count, not from any change in core arithmetic complexity.

Less materialization

No full dense Jacobian per batch row block when direct path applies, reducing memory writes and branch-heavy fill.

Plan reuse

Key-slot mapping and plan metadata are precomputed and reused, reducing repeated index lookups in hot loops.

Fewer temporary allocations

Direct update avoids intermediate dense matrices for the dominant batch-only path.

Predictable control flow

Most checks happen once during plan build; elimination runs in tighter loops over fixed structures.

5.1 Why this can reach ~10%+ in batch-heavy workloads

Batch-heavy systems spend a high percentage of time on factor ingestion and Jacobian layout updates. By moving work to direct, pre-mapped information updates, the implementation removes repeated overhead before numerical elimination. This is the primary source of observed uplift and the motivation for this path.

6) What is and is not batch-capable in this infrastructure

FeatureStatus in current infrastructureImpact
Direct hessian update for non-QR batch factors Supported High uplift in all-batch or mixed cliques with reusable plans.
Direct hessian for constrained batch factors Not supported Falls back to standard conversion behavior.
Mixed batch + Jacobian factor cliques Supported (partial) Direct factors update first, remaining rows fold through Ab_ path.
QR solve mode Compatible Uses QR behavior; direct batch is disabled by design.
Unary constrained factors (Jacobian) Supported by solver preprocess Constraint handling remains in established constrained-flow.

7) Biggest next improvements

  1. Make direct-batch switch a runtime or benchmark-tuned threshold instead of global compile-time behavior.
  2. Split planner logic into direct/QR/mixed buckets with explicit heuristic metadata for small/large cliques.
  3. Reduce pointer chasing in batch payload access and make mapped-slot arrays contiguous POD blocks to improve cache locality.
  4. Specialize most common block signatures (common ErrorDim/BlockDims...) and generate direct kernels for them.
  5. Add branchless checks for constrained/fixed-key eligibility and emit a compact per-factor eligibility bitmask in the plan.
  6. Collect a benchmark matrix by row-density and clique size to tune when to use full-direct vs mixed/direct-only fallback.

9) End-to-end flow summary

// End-to-end conceptual flow
for each gaussian factor graph build:
  - Precompute once: validate factor types and fixed keys
  - Build/update clique load plans (slot map + direct eligibility)
  - fillAb(): scatter batch rows only when needed
  - prepareForElimination():
      if direct batch route available:
        call direct Hessian updates from mapped slots
      else:
        keep legacy row-based accumulation
  - factorize and solve
  - reorder/merge as before, behavior unchanged

10) Closing

This document now describes the entire batch-factor infrastructure, not just the BatchJacobianFactor class. The key speed win still comes from the direct batch path in clique execution: precomputed plans + mapped slots + direct SymmetricBlockMatrix updates. This is what made the thread’s batch improvements materially competitive.
